### Q-AI-05 · [to:전원] · 결정됨(D-19)
- 질문: 모드를 고른 뒤 클립을 어떤 흐름으로 생성할까?
- 선택지: A. 전부 자동 생성하고, 완성된 것부터 피드에 표시 (팀장 에이전트 추천: 쇼츠 경험에 가깝다. 대신 클립 수 상한이 필요하다) / B. 첫 클립만 자동, 나머지는 사용자가 고른 것만 / C. 목록을 보여주고 사용자가 고른 것만
- 배경: 팀 논의에서 "사용자가 선택" 의견과 "전체 자동 분할 후 선택" 의견이 있었다.
- 작성: AI/Claude, 2026-11-06
- 답: D-19로 확정 (강현, 2026-11-09 회의)
  - **BE 의견 (BE/ChatGPT, 2026-11-06 · 미확정):** 초기에는 **B안(첫 클립 자동 생성, 나머지는 선택 생성)**을 추천합니다. Outline 전체는 먼저 보여주고, 실제 설계도·TTS 호출은 첫 클립부터 진행하면 사용자가 첫 결과를 확인할 수 있고 불필요한 유료 생성·대기열 폭증을 줄일 수 있습니다.
  - **추가 논의 필요:** B안은 쇼츠처럼 계속 넘겨 보려는 핵심 경험을 약화시킬 수 있습니다. A안(제한된 개수 자동 생성)은 몰입감에 유리하지만 비용·시간·동시 작업 부하가 증가합니다. AI 담당자가 클립당 실제 생성 시간·요금을 측정하고, FE가 '선택 생성'과 '연속 피드' 중 사용자 흐름을 비교한 뒤 결정하는 것이 좋겠습니다. A안 채택 시에도 클립 수 상한·중복 요청 방지·작업 큐가 필요합니다. 기존에 논의했던 개념 선택 흐름 역시 이 결정에 영향을 줍니다.
  - **AI 의견 (AI/Claude, 2026-11-07):** A안(팀장 의견에 동의). 모드를 고르면 클립 전체를 피드 순서대로 만들고, 완성된 것부터 바로 볼 수 있게 한다. 넘기다가 아직 안 만들어진 클립을 만나는 일을 줄이려면: (1) 여러 클립을 동시에 만든다(예: 4~5개씩). 사람이 클립 하나를 보는 데 약 1분이 걸리는데, 동시에 만들면 그보다 빨리 만들어진다. (2) 사용자가 앞으로 건너뛰면 그 클립을 먼저 만든다. (3) 아직 안 된 클립은 "만드는 중" 화면과 남은 시간을 보여준다. 클립 수 상한(Q-AI-03)은 그대로 필요하다. 클립당 실제 생성 시간은 실험에서 잰다. 동시 생성 개수는 API 계정의 요청 한도(rate limit)도 확인해야 한다.
  - **FE 의견 (FE/Codex, 2026-11-08 · 사용자 확인, 팀 최종 결정 전):** 전체 클립을 자동 생성하고 완성된 것부터 재생하는 A안을 지지한다. 목록과 연속 피드를 함께 제공하고 미완성·실패 상태를 구분한다. 클립 수와 동시 생성 상한은 실측과 서버 제약에 맞춰 정한다. 예상 시간은 근거가 있을 때만 표시한다.

    - 단계가 달라지는 Job은 3종류이고 `jobId`를 받는 곳이 다르다: `prepare`(업로드 응답·`GET /lectures/{id}`의 `preparationJobId`), `outline`(Outline의 `jobId`), `clip`(Outline `clips[].jobId`).

      | Job `type` | `stage` 순서 |
      |---|---|
      | `prepare` | `queued` → `starting` → `extracting` → `describing` → `finished` |
      | `outline` | `queued` → `starting` → `planning` → `finished` |
      | `clip` | `queued` → `starting` → `blueprint` → `audio` → `finished` |

    - **FE 후보 문구와 stage 대응(제안):** PDF 읽는 중=`extracting` · 페이지 내용 분석 중=`describing` · 학습 클립 구성 중=`planning` · 시각화 구성 중=`blueprint` · 음성 만드는 중=`audio`. 5단계가 BE 값과 1:1로 맞는다.
    - 실패는 `failed`, 실행 중 서버 재시작은 `interrupted`(둘 다 `status:"failed"`, 사유는 `error.message`).
    - **화면 문구 제안(최종 표현은 FE가 정한다):** `queued` 순서를 기다리는 중 · `starting` 작업을 시작하는 중 · `extracting` PDF 내용 추출 중 · `describing` 페이지 정보 분석 중 · `planning` 학습 클립 구성 중 · `blueprint` 영상 설계 중 · `audio` 음성 생성 중 · `finished` 완료 · `failed` 실패(`error.message` 표시) · `interrupted` 서버가 다시 시작돼 중단됨.
    - **FE가 알아 둘 것:** ① 빠른 단계는 3초 조회 사이에 지나가 못 볼 수 있다. ② 모르는 `stage`는 일반 문구로 보여 준다(값이 늘 수 있다). ③ 업로드 뒤 보이는 단계는 `prepare` Job, 모드 선택 뒤는 `outline` Job이고, 그 뒤 클립마다 `clip` Job이 자동으로 생겨 **클립별 단계가 다르다**(동시 실행 1개라 `queued`로 기다리는 클립도 있다). ④ 샘플 모드의 `describing`은 해설을 만들지 않고 지나가므로 거의 보이지 않는다. 샘플 결과는 실제 AI 생성이 아니다.

  - **FE 구현 보고 (FE/Codex, 2026-11-13 · 사용자 승인으로 main 병합):** BE의 기존 stage 표를 사용해 준비·분할·클립별 진행 문구와 짧은 일반 학습 팁을 연결했습니다. 실행 중인 클립의 jobId만 순차 GET 조회하고 대기·완료 클립에는 불필요한 추가 조회를 하지 않습니다. 가짜 퍼센트와 임의 단계 진행은 없으며, 모르는 stage는 일반 문구로 표시합니다. 완료 클립 재생은 유지합니다. 샘플을 실제 AI 분석으로 표현하지 않습니다. 빌드·FE 테스트 15개 통과, 브라우저 조작은 미확인입니다. 신규 API·유료 호출·생성 재시도는 추가하지 않았습니다.
