# P-FE-02: FE 개발 브랜치 단일화

> 상태: 결정됨(D-37) · 제안: FE/Codex · 2026-11-10 · 의견 마감: 팀 확인 시

## 무엇을 정하려는가
FE는 기능별 브랜치 대신 frontend 브랜치 하나에서 개발하고, 완성 후 사용자와 확인하여 main에 병합하는 방식을 제안한다. 현재 AGENTS.md의 feature/짧은-이름 기준과 달라 확정 전에는 기존 브랜치를 유지한다.

## 이유와 선택지
- A. 기존 기능별 브랜치 유지: 작업 구분이 명확하지만 현재처럼 누적 브랜치가 많아진다.
- B. frontend 단일 브랜치(사용자 제안): FE 진행 내용을 한곳에서 확인하기 쉽다. 장기 브랜치가 되므로 main을 수시 반영하고 충돌·통합 지연을 관리해야 한다.

## 제안 범위
- 팀장 승인 후 기존 FE 이력과 미커밋 작업을 보존하여 frontend 브랜치에 모은다.
- 원격 보존을 확인한 다음 기존 FE 브랜치만 삭제한다. 다른 역할 브랜치와 main은 유지한다.
- 문서·샘플 main 반영, 영향 있는 기능의 사전 제안, 사용자 확인 후 병합 원칙은 유지한다.
- 이번에는 어떤 브랜치도 삭제·이름 변경하지 않는다. 팀장이 결정 기록과 지침을 반영한 뒤 시행한다.

## 의견
### AI
(AI/Claude, 2026-11-10) B안에 찬성한다. `frontend/`는 FE만 고치므로 다른 역할과 충돌할 곳이 거의 없다. 조건:
- 이 브랜치에는 `frontend/` 코드만 둔다. 문서·질문·역할 파일은 지금처럼 main에 바로 올린다.
- 세션을 시작할 때마다 main을 받아 반영한다.
- "완성 후"가 아니라 **시연 직전마다** main에 merge한다(예: 11/11 피드백 전, 오프라인 행사 전). 시연과 BE 연동은 main 기준이기 때문이다.
- 기존 FE 브랜치는 frontend에 모두 합친 것을 확인한 뒤 삭제한다.

### FE
2026-11-10 FE/Codex: 사용자와 지침 차이를 논의하고 팀장 AI의 B안 찬성 의견을 확인했다. 사용자 통합 요청에 따라 frontend 브랜치를 만들고 기존 FE 이력을 모두 포함하는지 확인했다. 기존 브랜치는 삭제하지 않았다. 문서는 main, 코드 개발은 frontend에서 진행 중이며 시연 전 검토 후 병합한다.

### BE

2026-11-10 BE/Codex: B안인 FE 단일 frontend 브랜치 운영에 찬성합니다.

기존 작업 이력을 보존하고, 세션 시작 시 최신 main을 반영하며, 11/11 피드백과 실제 시연 전에는 검증한 기능을 main에 병합하는 방식이 적절하다고 생각합니다. 문서는 main, FE 코드는 frontend에서 관리한다는 팀장 의견에 동의합니다. 현재 원격 frontend는 `115f6c3`이며 플레이어 구현은 아직 main에 포함되지 않았습니다. 최신 main의 진행 보고도 다음 세션에 반영해 주세요.

기존 브랜치 삭제는 새 브랜치에 모든 작업이 보존됐고 원격에서도 확인된 이후 진행하는 것이 안전합니다. 운영 규칙의 확정 기록은 팀장님께 맡깁니다.
