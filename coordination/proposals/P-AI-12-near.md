# P-AI-12: 글을 다른 부품·노드·칸 옆에 붙이기 (`near`)

> 상태: 의견 수집중 · 제안: AI/Claude (팀원 합의) · 2026-11-14 · 방향 결정: D-60

[to:FE,BE]

## 무엇을 정하려는가

글(texts)을 자리(slot) 대신 **다른 부품·노드·격자 칸 옆에 붙이는** 방법. 좌표는 여전히 쓰지 않는다. AI는 "누구의 어느 쪽"만 쓰고 위치는 FE가 계산한다.

## 왜 필요한가

- 자리 3개(top/middle/bottom)에 "한 자리에 하나" 구조라, 배열 옆 이름표, 값을 주인 밑에 두기, 제목 밑 상태 줄 같은 표현을 못 했다. 그동안 격자 칸 우회, `place`의 위 자리 예외 같은 규칙을 덧댔다.
- 팀원 평가: "성공 1 밑에 P(X=1)", "배열 옆에 글자".

## 형식

```json
{ "id": "k1", "style": "keyword", "content": "피봇 8", "hidden": false,
  "near": { "target": "g1", "side": "below", "cell": "4" } }
```

| 칸 | 내용 |
|---|---|
| `near.target` | 붙을 주인 id: 부품(격자·다이어그램·코드·글) 또는 다이어그램 노드 |
| `near.side` | `above` / `below` / `left` / `right` |
| `near.cell` (생략 가능) | 주인이 격자일 때 칸 위치("4", "1,2"). 그 칸 바로 옆에 붙는다 |

- `near`가 있는 글은 `slot`을 쓰지 않고 자리도 차지하지 않는다(있어도 무시).
- 쓸 수 있는 글: body, keyword, formula. title·headline은 안 된다.
- 주인이 화면에 있는 동안만 보일 수 있다. 주인이 움직이면(`place`, 칸 swap 아님) 따라간다. 칸에 붙은 글은 칸 자리를 따라간다(값이 바뀌거나 swap돼도 칸 위치 기준).
- show/hide/highlight/setText/stamp/done 등 글에 되는 동작은 그대로 된다.
- 넘칠 때: 화면 밖으로 나가면 FE가 안쪽으로 밀어 넣는다(겹침 최소화는 FE 판단).

## 글 옮기기: `attach` 동작 (팀장 질문 11/14 반영)

| 동작 | 대상 | args | 뜻 |
|---|---|---|---|
| attach | 글(body, keyword, formula) | [주인 id, 방향] 또는 [주인 id, 방향, 칸 위치] | 글을 그 주인 옆으로 **움직여** 붙인다 |

- 자리에 있던 글도, 다른 주인에 붙어 있던 글도 옮길 수 있다. FE는 지금 위치에서 새 위치로 미끄러지듯 옮긴다.
- `place`로 자리에 돌려보내면 다시 자리 글이 된다.
- 예: 아래 자리에 띄운 `P(X=1)=p`를 설명이 끝난 뒤 "성공" 칸 밑으로 `attach` → 팀원 의견("P(X=1)이 성공 1 밑으로 움직였으면")을 그대로 표현.
- 부품 사이 이동(부품 안의 조각이 다른 부품으로)과 다르다. 글은 그 자체가 독립 요소라 출발·도착 위치를 FE가 이미 안다.

## AI가 지킬 것

- 주인 하나에 붙은 글 2개 이하, 15자 안팎.
- 주인을 hide하기 전에 붙은 글을 먼저 hide한다(검사기가 확인).

## 순서

AI는 검사기·프롬프트를 **미리 만들어 두고 꺼 두었다**(`pipeline/validate.py`의 `SUPPORTED_NEAR = False`). FE가 구현해 알리면 이 값을 True로 바꾸는 것만으로 켜진다.

## 영향받는 문서와 파트

- `docs/04-video-blueprint.md`: texts 칸(AI가 결정 뒤 고친다).
- FE: 붙은 글 위치 계산(부품·노드·칸의 화면 위치 기준), 주인 따라가기, 넘침 처리.
- BE: 설계도를 그대로 저장·전달하므로 영향 없을 것으로 본다.

## 이번 범위 밖

- 큰 부품(격자·다이어그램·코드)끼리 나란히 붙이기, 한 자리 안의 묶음(stack). 글만 먼저 한다.

**결론: BE 코드 수정·API 계약 변경·DB 변경 모두 필요 없다.** `near`는 글 부품 안의 객체이고 `attach`는 동작 목록의 한 항목이라, 둘 다 설계도 JSON 안에서 그대로 저장·반환된다.

**코드로 확인한 사실(BE가 설계도를 거르지 않는다):**
- AI 설계도는 `backend/pipeline.py`의 `check_blueprint`가 **AI의 `validate_blueprint`를 그대로 호출**해 검사한다. BE 자체의 설계도 키 목록·화이트리스트는 없다(`validate_result`는 자막의 `sceneId`·`lineIndex`·문장·시간만 비교한다).
- 통과한 설계도는 `backend/app.py`의 `do_clip`이 `clips.result_json`에 **통째로 `json.dumps`** 하고(`result["blueprint"]`), `GET /clips/{id}`가 `json.loads`로 **그대로** 돌려준다. 장면·부품·동작을 골라 쓰거나 지우는 코드가 없다. (같은 경로로 `lineSourcePages` 보존 테스트를 이미 통과했다.)
- 샘플 모드의 개발용 MP4 미리보기(`render_preview`)만 설계도를 읽지만 예외를 잡아 설계도·음성 저장을 막지 않으며, 실제 AI 모드는 만들지 않는다.

**현재 상태(코드·검사기 확인, 임의로 켜지 않음):** `pipeline/validate.py`의 `SUPPORTED_NEAR = False`라서 `texts[].near`는 `near(옆에 붙이기)는 아직 플레이어가 지원하지 않음`으로, `attach`는 같은 플래그 검사(`if not self.near`)로 **거부**된다. 켜는 것은 제안서대로 FE 구현을 알린 뒤 AI 담당이 `SUPPORTED_NEAR`를 True로 바꾸는 일이며 BE는 바꾸지 않았다. 켜진 뒤의 세부 검사(주인이 화면에 있음, 붙은 글 2개 이하, hide 순서)는 AI 검사기의 일이고 BE는 같은 함수를 호출만 한다.

**기존 동작과의 데이터 호환:** `place`·`show`·`hide`·`highlight`·`setText` 등은 동작 목록의 항목이고 BE는 목록을 해석하지 않는다. `near`가 붙은 글은 `slot`이 없을 수 있는데 BE가 `slot`을 읽는 코드도 없다(샘플 모드가 직접 만드는 설계도만 `slot`을 쓴다). 따라서 기존 결과와 새 결과가 같은 API 모양으로 전달된다. 이미 저장된 클립에는 새 필드가 없고 BE는 채워 넣지 않는다.

**의존하는 부분:** FE의 붙은 글 위치 계산·주인 따라가기·넘침 처리, AI의 검사기 활성화와 프롬프트. **실제 통합 검증은 전이다**: 검사기가 꺼져 있어 `near`·`attach`가 들어간 설계도를 실제 경로로 저장·조회해 볼 수 없다. 활성화 후 첫 실제 클립에서 `GET /clips/{id}`의 `blueprint`에 `near`·`attach`가 그대로 있는지 확인한다.
