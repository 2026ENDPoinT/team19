# P-BE-01: 데이터 저장 정책과 단계적 시연·배포 전략

> 상태: 의견 수집중 · 제안: BE/ChatGPT · 2026-11-06 · 의견 마감: 팀 협의 시 결정

## 무엇을 정하려는가

- Q-AI-08: 업로드한 PDF, 분석 결과, 클립 설계도·음성 등을 어디에 얼마나 보관할지.
- Q-AI-12: 초기 해커톤 시연을 로컬에서 할지 공개 배포할지, 그리고 이후 배포 전환을 어떻게 준비할지.

**추천 요약:** 초기에는 SQLite + 로컬 파일 저장소로 **실제 작동하는 MVP**를 만들고, 로컬 노트북에서 시연합니다. 동시에 자동 보관·정리 정책과 외부 배포로 전환할 수 있는 경계를 설계합니다. 이는 BE의 제안이며 확정 결정이 아닙니다.

## 왜 지금 필요한가

- 팀의 1단계 목표는 PDF 업로드 → AI 처리 → 클립 설계도·음성 생성 → 저장 → 브라우저 재생이며, 서버 재시작 후에도 결과가 남아야 합니다(`docs/01-product.md`, `coordination/roles/be.md`).
- 2단계에는 '내 강의함'과 클립 재생성이 있습니다. 원본 PDF를 생성 직후 지우면 재생성에 필요한 정보가 부족할 수 있습니다.
- 현재 로그인은 3단계로 미뤄졌습니다. 공개 배포하면서 '내 강의함'에 모든 강의를 보여주면 다른 사용자의 자료가 노출될 수 있어, 인증·소유권·접근 제어까지 고려해야 합니다.
- 11/11 현직자 피드백에서 “왜 로컬에서만 시연하나?”, “MVP인데 파일 관리가 수동인가?”, “배포할 때 다시 만들어야 하나?”라는 질문에 설계와 검증 결과로 답하고 싶습니다.

**MVP와 시연용 모형의 구분:** MVP는 핵심 흐름이 실제 입력으로 동작하는 최소 제품입니다. 미리 저장한 결과를 재생하는 예비 시연 모드는 장애 대비책이지, 실제 AI 생성 기능을 대체하지 않습니다.

## 선택지

### A. SQLite + 로컬 파일 저장, 로컬 시연 우선 (추천)
- 장점: 외부 DB·스토리지 운영 없이 PDF 처리와 작업·결과 영속성을 먼저 검증하고, 현장 오류를 팀이 직접 추적하기 쉽습니다. 공개 서비스에 필요한 인증이 아직 없는 상황과도 맞습니다.
- 단점: 노트북 한 대의 저장소와 실행 환경에 의존합니다. 저장 공간·파일 수명 주기·백업을 자체적으로 관리해야 하고, 외부 사용자는 바로 접속할 수 없습니다.

### B. 서버형 DB + 클라우드 파일 저장, 인터넷 배포부터 진행
- 장점: 외부 접속·다중 사용자·확장 실험을 일찍 시작할 수 있습니다.
- 단점: 인증·사용자별 데이터 소유권, 배포 설정, API 비용·파일 접근 제어 등이 필수로 늘어나 핵심 영상 생성 흐름 검증이 늦어질 수 있습니다.

### C. 저장 없이 시연용 샘플만 보여주기
- 장점: 빠르게 화면을 보여줄 수 있습니다.
- 단점: PDF 처리, 재시작 후 결과 유지, 실패 처리 등 실제 MVP의 핵심을 검증하지 못합니다. **정상 구현 방식으로는 추천하지 않고, 장애 시 예비 시연에만 사용**합니다.

## 제안자의 추천과 이유

### 1. 저장 구조: 작게 시작하되 자동으로 관리

- **SQLite:** Lecture, Page, Outline, ClipPlan, Clip, Job 등의 ID·상태·생성 시각·파일 참조를 관리합니다. 현재 데이터 모델과 계약은 초안이므로 구체적인 테이블과 필드 이름은 계약 v0에서 정합니다.
- **파일 저장소:** PDF 원본, 페이지 이미지, 음성 파일 등을 로컬 폴더에 저장합니다. Blueprint는 JSON으로 직렬화하고, SQLite에 둘지 파일로 분리할지는 팀 협의 후 결정합니다.
- **영속성:** 서버 종료·재시작 후에도 강의 목록, 클립 결과, 작업 상태를 복구할 수 있게 합니다. 처리 중 종료된 Job을 어떻게 복구·실패 처리할지도 별도 규칙으로 정합니다.
- **보관:** 원본 PDF는 영상 생성 즉시 삭제하지 않습니다. 강의 다시 보기·클립 재생성에서 원본이나 페이지 그림이 필요한지 AI 담당과 확인하고, 보관 기간을 팀에서 정합니다.
- **파일 수명 주기:** 만료 시각 등을 기록하여 **자동 정리 기능을 구현 목표에 포함**합니다. 우선 서버 시작 시 만료 파일 검사 같은 단순한 방식부터 고려하고, 필요하면 주기 실행을 추가합니다. 처리 중인 작업과 시연용 샘플은 보호하고, 삭제 실패 시 DB와 파일 간 불일치를 추적·재시도할 수 있게 합니다.
- **우선순위:** PDF 업로드·저장·재시작 후 복구·오류 처리는 **1단계 필수**. 자동 보관·정리는 **높은 우선순위의 후속 구현 목표**로 두되 전체 흐름을 해치면서 먼저 만들지는 않습니다. 구현 전에는 운영상 임시 정리 방식을 명시하고 자동화가 완료됐다고 주장하지 않습니다.
- **안전:** 업로드 파일명으로 실제 저장 경로를 만들지 않고 고유 ID를 사용합니다. 파일 형식·크기를 검증하고, 파일 경로를 프론트엔드에 직접 노출하지 않습니다.

### 2. 시연: 단일 사용자 로컬 MVP + 장애 대비

- **현 단계 추천:** 시연용 노트북에서 프론트엔드와 백엔드 서버를 함께 실행하고 로컬 DB·파일을 사용합니다. 정상 시연은 **새 PDF 입력 → AI 분석 → 생성 결과 저장 → 브라우저 재생**까지 실제로 동작해야 합니다.
- **로컬 선택의 기술적 이유:** 로그인·접근 제어가 없는 '내 강의함'을 인터넷에 그대로 공개하면 사용자 자료가 섞이거나 노출될 수 있습니다. 인증을 갖추기 전에는 단일 사용자 로컬 범위에서 핵심 기능을 검증하는 편이 안전합니다.
- **예비 시연:** 인터넷 또는 외부 AI API 장애를 대비해 사전 생성된 결과 2~3세트를 저장해 재생합니다. 이는 **미리 생성된 결과를 보여주는 백업 시나리오임을 명확히 알립니다**. 오프라인 시연은 로컬 프론트엔드·백엔드·정적 자산·음성이 모두 외부 서비스 없이 실행되는지도 확인해야 합니다.
- **시연 방식 변경 조건:** 심사위원이 자기 기기에서 접속해야 하는 등 외부 접속이 필수인 경우, 팀장 및 행사 규정을 확인하고 인증/접근 제어를 포함한 배포 범위를 재검토합니다.

### 3. 향후 배포에 대비해 지금부터 준비할 경계

| 현재 단계 | 미리 준비할 구조 | 향후 확장 시 필요한 추가 작업 |
|---|---|---|
| SQLite | DB 접근 코드를 API 처리 로직과 분리 | PostgreSQL 등으로 스키마·데이터 마이그레이션 |
| 로컬 파일 | 파일 저장·조회 함수를 별도 모듈로 분리, 클라이언트는 API를 통해 파일 이용 | S3 호환 저장소, 접근 제어·URL 정책 |
| 로컬 서버 | API 주소와 파일 경로를 환경 설정으로 관리 | 호스팅, HTTPS, CORS, 비밀키·운영 설정 |
| 단일 사용자 강의함 | 강의 식별자와 조회 흐름을 일관되게 설계 | 로그인, owner/user ID, 권한 검증, 사용자별 목록 필터 |
| 간단한 작업 처리 | Job 상태를 DB에 남기고 실패를 표현 | 작업 큐, 별도 실행기, 재시도·중복 방지·모니터링 |

**확장 가능하게 설계한다는 뜻은 “설정만 바꿔 즉시 배포 가능하다”는 뜻이 아닙니다.** 실제 공개 배포에는 인증, 보안 검토, 데이터 이전, 운영 테스트가 추가로 필요합니다. 다만 지금부터 DB·파일·API 경계를 분리하면 기존 핵심 로직의 재사용 가능성을 높일 수 있습니다.
